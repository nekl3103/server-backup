# Руководство пользователя Server Backup 1.9.1

[Вернуться к README](../README.md)

## 1. Подключение сервера

На стартовом экране нажмите **«Добавить сервер»**. Укажите название, адрес, SSH-порт, пользователя и при необходимости группу. Для пароля используется Keychain; для SSH-ключа выберите файл и задайте парольную фразу, если ключ зашифрован.

Для административных действий нужны root или пользователь с `sudo -n`; во втором случае включите соответствующий переключатель. При первом подключении сверьте показанный отпечаток SSH с ключом сервера, полученным через доверенный канал. Если ключ изменился, сначала выясните причину.

Откройте сервер нажатием на карточку или строку таблицы. Обзор показывает систему, инструменты, хранилища и готовность настройки. В случае отсутствия Restic/помощника нажмите установку инструментов. Повторная настройка не удаляет существующие задания.

Через **«Все серверы»** можно вернуться к списку и добавить следующее подключение. Поиск, группы и фильтры помогают работать с большим количеством серверов. «Доступен» описывает SSH-связь, а статус копий — состояние бэкапов: это разные показатели.

## 2. Хранилища

У сервера может быть несколько подключений. Сохранённое подключение отображается карточкой; форма открывается при добавлении или изменении. Создание нового репозитория и подключение существующего — отдельные действия. Ошибка сети/пароля не означает, что репозитория нет.

### Диск или каталог сервера

Выберите существующую точку подключения и каталог. Для диска проверяются точка подключения/UUID, размер и свободное место. Перед копированием проверяется ожидаемый диск, чтобы при его отсутствии не записать бэкап в каталог системного диска. Приложение не форматирует диски и не создаёт разделы.

Хранилище желательно размещать отдельно от выбранных источников. Сам репозиторий исключается из резервирования. Если сервер и единственный локальный диск потеряны одновременно, нужна другая доступная копия для восстановления.

### SFTP — другой сервер

Укажите адрес, порт, пользователя и абсолютный каталог хранения. Создайте отдельный ключ для резервирования, установите публичную часть на сервер хранения и подтвердите его SSH-ключ. Проверьте доступ, затем создайте либо подключите репозиторий.

После настройки сервер-источник обращается к SFTP самостоятельно. На новом сервере для восстановления нужен собственный разрешённый ключ доступа к тому же каталогу.

### S3

Укажите HTTPS endpoint, бакет, префикс, регион и ключи. Например: endpoint `https://s3.example.com`, бакет `backups`, префикс `server-01`. Для выбранного префикса требуются операции чтения, записи, списка и удаления при очистке. S3 не монтируется как диск.

Не удаляйте объекты Restic по возрасту средствами Lifecycle: старый блок может использоваться свежим снимком. Для разных серверов используйте отдельные префиксы.

### Яндекс Диск

Подготовьте поддержку rclone, затем пройдите вход в Яндекс через браузер. Сохраните полный JSON токена, включая refresh_token, когда его предоставляет вход. Одиночного access_token может быть недостаточно для обновления доступа.

Укажите папку, например `ServerBackup/server-01`, и проверьте доступ/свободное место. После этого отдельно создайте либо подключите репозиторий Restic. Токен и пароль репозитория — разные секреты.

Ошибка refresh_token требует повторного входа и полного результата авторизации. Ошибка доступа не создаёт репозиторий автоматически. Приложение не очищает общую корзину аккаунта Яндекс Диска; удалённые объекты могут продолжать занимать место там.

## 3. Что сохранять и когда

В **«Заданиях»** сначала показываются сохранённые задания. Нажмите на конкретное задание для его данных и настроек либо **«Новое задание»** для создания.

1. Выберите основное хранилище.
2. Задайте понятное название; технический ID используется в серверных службах.
3. Открывайте папку нажатием имени. Галочка выбирает объект, кнопка выбора текущей папки — весь каталог.
4. Добавьте нужные смонтированные файловые системы. Выбор `/` не означает включение всех подключённых дисков.
5. Укажите исключения: пути либо маски, по одному в строке. Например, `*.tmp`.
6. Включите нужные подключения БД и режимы Docker.
7. Выберите время по часовому поясу сервера, срок хранения и при необходимости ограничения скорости/параллелизма.
8. Сохраните, выполните пробный запуск, затем настоящий бэкап.

По умолчанию запуск ежедневно в 03:00, 14 ежедневных и 4 еженедельных копии. Таймер может добавить до 10 минут случайной задержки. Очистка и проверка структуры выполняются по воскресеньям после успешного бэкапа; неполная копия не запускает автоматическую очистку.

Системные виртуальные файловые системы, временные каталоги, секреты помощника, репозиторий и живые системные файлы БД исключаются. Дампы и явно выбранные Docker-тома добавляются отдельно.

Изменение настроек требует сохранения перед запуском. История показывает изменения и следующий запуск. **«Приостановить»** выключает расписание, но не отменяет уже работающий бэкап. **«Дублировать»** создаёт выключенное задание для проверки и последующей настройки.

### Дополнительные направления

Отметьте другие подключённые хранилища в задании. После основной копии Restic copy переносит снимок в каждое направление. Это копирование данных сервером, поэтому Mac не нужен. Совпадающие блоки в репозитории назначения повторно не передаются.

Основная копия может быть успешной, а дополнительная — завершиться ошибкой. В операции и центре ошибок отображаются оба результата. Автоматическая очистка дополнительных направлений отдельно этим механизмом не настраивается. Copy между S3 с разными ключами требует общего ключа с доступом к обоим репозиториям при текущем способе запуска Restic.

## 4. Базы данных

### Согласованные дампы

Добавьте соединение MySQL, MariaDB или PostgreSQL и проверьте доступ. Выберите все или конкретные базы, затем включите подключение в задании. Сохраняются дампы и версии СУБД.

Для InnoDB используется транзакционный дамп. Для нетранзакционных таблиц выберите блокировку: обычный транзакционный режим отклоняется. Во время дампа не выполняйте изменения структуры таблиц. PostgreSQL сохраняет роли и отдельные базы в custom-формате; дампы нескольких баз не являются одной общей транзакцией.

Для локальных баз нужны соответствующие клиентские утилиты. Для подключения внутри Docker инструменты запускаются в выбранном контейнере. Наличие работающих файлов `/var/lib/mysql` или `/var/lib/postgresql` в файловой копии не заменяет согласованный дамп.

### Базовая копия + изменения

Выберите соответствующий режим подключения. Первая копия создаёт базу, следующие добавляют закрытые binlog/WAL. Каждый снимок содержит необходимые части своей цепочки: для восстановления выбранного снимка старый сервер не нужен.

| СУБД | Требования и поведение |
| --- | --- |
| MySQL | binlog включён, формат ROW, права чтения журналов и FLUSH BINARY LOGS; mysqlbinlog и mysqldump той же ветки, что сервер |
| MariaDB | binlog включён, ROW, права журналов/ротации и подходящий mariadb-binlog; для нетранзакционных таблиц нужна блокировка |
| PostgreSQL | wal_level/архивирование WAL/full_page_writes настроены заранее, доступен отдельный каталог архива, pg_basebackup и сервер одной основной версии; внешние tablespaces не поддерживаются этим режимом |

В журнальном режиме сохраняется **весь экземпляр/кластер БД**, а не отдельная выбранная база. Нужен прямой TCP-доступ; Docker поддерживается через доступный опубликованный порт, а не docker exec. Peer-доступ в этом режиме не поддерживается. Приложение проверяет условия и не меняет настройки журналирования работающей БД.

Локальная база и закрытые журналы занимают место на сервере до явного создания новой базовой копии. При смене источника, нарушении последовательности или отсутствии нужного журнала задание завершается ошибкой.

### Восстановление БД

Сначала восстановите файлы копии в отдельный каталог. Затем выберите БД из манифеста и задайте целевые доступы. Импорт выполняется отдельным подтверждённым действием; цель может быть изменена частично при ошибке.

Для журнальной копии можно указать момент восстановления с часовым поясом внутри доступного диапазона. Пустое значение означает конец сохранённой цепочки. MySQL/MariaDB импортируют базу и журналы в указанный экземпляр. PostgreSQL подготавливает отдельный пустой PGDATA и настройки recovery; запуск и перенос сервиса выполняются отдельно. Перед запуском проверьте порты, расширения, SSL и внешние пути.

## 5. Docker

Для проекта доступны контейнеры, Compose-метаданные, bind mounts и named volumes. Выберите режим каждого контейнера:

- **Дамп БД:** сначала настройте подключение СУБД и включите его в задание.
- **Остановить:** работающий выбранный контейнер останавливается на время копии, затем запускается после успеха, ошибки или отмены.
- **Копировать работающий:** данные сохраняются без гарантии согласованности; режим требует явной отметки.

Задание запоминает только контейнеры, которые остановило само. Состояние сохраняется в `/var/lib/server-backup/stopped`, используется при восстановлении после прерывания и следующем запуске сервера.

Для восстановления выберите контейнеры из манифеста, подготовьте остановленные целевые контейнеры и при необходимости замените пути bind mounts. Перезапись непустых томов требует отдельного разрешения. Проверьте Compose, порты, `.env` и подключения к БД. Запуск сервисов — отдельное явное действие.

## 6. Ход задания и результаты

Панель операции показывает текущий этап, обработанные/добавленные данные, длительность, прогресс, дополнительные направления и ошибки. Кнопка остановки отменяет серверную операцию; закрытие панели скрывает её, но не отменяет задание.

Бэкап, запущенный через systemd, продолжает работу при закрытии приложения и обрыве SSH. После возвращения приложение получает активное состояние и сохранённые результаты. Если сам сервер выключен, работа на нём не продолжается.

«Успешно» означает успешный бэкап. Неполная копия, ошибка очистки/проверки и ошибка уведомления показываются отдельно. Наличие успешной основной копии не скрывает проблему дополнительного направления.

## 7. Копии, версии и сравнение

Выберите хранилище и снимок по дате/ID. Дерево показывает пути, типы, размер, дату и права. Папки открываются нажатием имени; выбор для восстановления выполняется галочками. Первый индекс большой копии может готовиться долго, затем используется сохранённый серверный индекс.

**«История версий»** в свойствах файла показывает наличие, размер и дату изменения в разных снимках, по пять копий на странице. Кнопка восстановления выбирает конкретную версию. Это история метаданных; одинаковые дата/размер не доказывают одинаковое содержимое.

Сравнение снимков показывает добавленные, удалённые и изменённые объекты. Сравнение с текущим сервером сначала использует метаданные. **«Содержимое»** вычисляет SHA-256 выбранного обычного файла до 64 МБ. Для UTF-8 до 1 МБ выводится цветной текстовый diff с ограничением вывода. Ссылки и специальные файлы этим режимом не сравниваются; изменение файла во время чтения приводит к ошибке и необходимости повторить проверку.

Расширенные операции Restic находятся отдельно от обычного просмотра: check, stats, forget/prune, copy, ключи и блокировки. Поддержка команд зависит от установленной версии и дополнительных утилит. Разрушающие действия требуют явного подтверждения.

## 8. Восстановление файлов

Мастер состоит из трёх шагов: копия → сервер назначения → данные.

1. Выберите хранилище и дату копии. `latest` означает последнюю доступную версию, но для конкретного восстановления удобнее дата/ID.
2. Выберите исходный или новый сервер. Для нового подготовьте SSH, подтвердите ключ, проверьте систему/место и подключите тот же репозиторий.
3. В левой панели **«Откуда»** выберите всю копию либо папки/файлы. Имя папки открывает её, галочка выбирает.
4. В правой панели **«Куда»** выберите каталог. Для безопасной проверки используйте отдельную папку, например `/srv/server-backup-restore`.
5. Можно выбрать целевой файл для замены одним файлом копии. Существующие данные требуют разрешения перезаписи. Восстановление в корень тоже требует отдельного подтверждения.
6. Визуальный выбор по имени/типу помогает задать фильтр; ручные пути/маски находятся в расширенном блоке.
7. Проверьте результат, затем отдельно импортируйте БД/тома и включите сервисы при необходимости.

Если выбран `/srv/server-backup-restore`, исходный `/var/www/site` появляется внутри него с исходной структурой путей. Это не установка ОС или загрузчика. Недоступный единственный локальный репозиторий невозможно восстановить без другой копии.

## 9. Проверка восстановления

**Выборочный режим:** до пяти обычных файлов, суммарно до 32 МБ, восстанавливаются временно и проверяются Restic/SHA-256. Это быстрая ограниченная проверка, не проверка всей системы.

**Полный режим:** восстанавливаются все файлы, базы импортируются в новые изолированные Docker-контейнеры, тома копируются отдельно и Compose проверяется. Нужны отдельный тестовый сервер, свободное место для восстановления и заранее установленные официальные образы подходящих версий. Контейнеры без сети/опубликованных портов и временные данные удаляются после проверки.

Полная проверка не запускает восстановленный сайт или Compose-приложение. Дата последней успешной полной проверки отображается отдельно от выборочной. Автоматическую проверку после успешного задания можно включить в разделе проверки копий; она выполняется сервером без Mac.

## 10. Файлы, терминал, программы и Cron

**Терминал:** интерактивный SSH с вводом в экран, стрелками, Tab, Enter и Ctrl+C. Команды выполняются с правами SSH-пользователя; это прямое управление сервером.

**Файлы:** несколько объектов выбираются галочками, ⌘+кликом и Shift+кликом. Доступны загрузка файлов/папок перетаскиванием, скачивание, переименование, перенос, права, создание файла/каталога и обновление. Контекстное меню пустого места содержит действия каталога. Избранное даёт быстрые переходы.

Удаление файлов перемещает их в `.server-backup-trash` для восстановления; поэтому каталог корзины может появиться рядом с файлами. Перенос между файловыми системами и рекурсивный chmod не поддерживаются этим файловым режимом.

**Программы:** установленные dpkg/APT-пакеты с поиском и категориями «системные», «вручную» и «зависимости». Для установки показывается предварительный план; удаление пакетов не разрешается этим действием. Программы, установленные вне dpkg, могут отсутствовать в списке. Управление поддерживаемыми службами и редактирование конфигураций доступны отдельно. Перед записью проверяется, что исходный текст не изменился; есть история настроек.

**Cron:** просмотр пользовательских/системных задач и таймеров systemd. Для доступных записей можно добавлять и редактировать расписание с понятными полями либо использовать исходный cron-формат. Изменение проверяется на конфликт с параллельной записью; системные файлы и пользовательский crontab имеют разные форматы/права. Произвольные systemd-таймеры не превращаются автоматически в редактируемые cron-задачи.

## 11. Мониторинг и журнал

Мониторинг получает метрики через SSH-поток с выбранным интервалом: CPU, RAM, swap, load average, сеть и дисковый ввод/вывод. Основные физические диски показывают занятое/свободное место; подробности открываются нажатием. Виртуальные и повторные точки подключения не создают отдельные «диски» в сводке.

Процессы представлены таблицей и графиком; CPU из ps описывает среднее использование за время работы процесса и может превышать 100% у нескольких потоков. Недоступная метрика не считается нулевой. При разрыве сохраняются последние данные и время обновления. Постоянная серверная история нагрузки не ведётся.

Журнал содержит серверную историю операций с понятными названиями, результатом, заданием и хранилищем. Подробности открываются отдельно. Можно смотреть доступные серверные лог-файлы и следить за новыми строками онлайн. «Центр ошибок» разделяет ошибки бэкапа, очистки, проверки, Docker, дополнительных направлений и уведомлений; исправление причины не удаляет старые записи.

## 12. Ёмкость и уведомления

Измерение ёмкости — серверная операция: смена вкладки её не отменяет, остановка доступна отдельной кнопкой. Размер репозитория отличается от суммы размеров файлов всех снимков благодаря дедупликации.

Для прогноза нужны минимум два измерения с разницей не меньше часа. Предупреждение появляется при свободном месте меньше 5 ГиБ либо прогнозе меньше 7 дней. Для S3/SFTP задайте известную квоту, если провайдер не возвращает свободное место.

Telegram и почта необязательны. Настройте один или оба канала и отправьте тестовое сообщение. Telegram требует токен бота/chat ID, почта — параметры SMTP и адреса. Сообщения отправляет сервер. Ошибка уведомления не меняет результат бэкапа; успешные копии уведомляют только при включённом переключателе. Для стандартного ежедневного задания отсутствие свежей успешной копии больше 26 часов вызывает предупреждение.

## 13. Внешний контроль

Выберите сервер-наблюдатель и другие серверы для контроля. Приложение устанавливает отдельный ограниченный SSH-ключ, разрешающий получение состояния бэкапов, закрепляет ключи наблюдаемых серверов и настраивает таймер проверки примерно раз в 10 минут. Пароли SSH-профилей не копируются на наблюдателя.

Нажмите настройку, затем проверку сейчас; смотрите отдельный результат каждого сервера и состояние таймера. Уведомления отправляет наблюдатель через свои Telegram/SMTP-настройки. Если выключен сам наблюдатель, для обнаружения этого нужен другой независимый наблюдатель.

## 14. Доступы, экспорт и потеря Mac

Mac хранит SSH-секреты и секреты подключений в Keychain. Для автономных заданий необходимые доступы также сохраняются на Linux-сервере в файлах помощника с ограниченными правами. Корневой доступ к серверу позволяет прочитать эти настройки.

Через **«Экспорт / импорт»** создайте зашифрованный экспорт профилей и секретов с отдельным паролем. Для восстановления на другом Mac импортируйте экспорт и подтвердите доступы. Экспорт включает выбранные приватные SSH-ключи и подтверждённые ключи серверов; при импорте ключи восстанавливаются в каталог приложения с правами 0600. Сохраните экспорт и его пароль отдельно от единственного компьютера.

Для восстановления данных после потери сервера нужны доступ к репозиторию и его пароль. Профиль источника не заменяет недоступный диск с единственной копией.

## 15. Ошибки подключения и установки

- **Неизвестный/изменённый host key:** проверьте отпечаток и подтвердите его отдельным действием.
- **«Нет связи»:** проверьте адрес, порт, сеть и SSH-доступ. В 1.9.1 ошибка одного канала/репозитория не должна объявлять весь сервер недоступным без независимой проверки подключения.
- **NO_PUBKEY / отсутствующий Release стороннего APT:** инструменты бэкапа устанавливаются через временные подписанные источники ОС; системные Docker/Yarn/NodeSource-источники не исправляются этим способом.
- **Нет официального ключа ОС или выпуск недоступен:** установка прекращается, подпись не отключается. Нужно восстановить штатный пакет ключей/поддерживаемые источники ОС.
- **Неизвестный флаг Restic:** проверьте установленную версию и доступность функции; приложение учитывает поддержку dry-run и read-concurrency.
- **Журнальная БД не прошла проверку:** проверьте версии клиентских утилит, права и binlog/WAL. MySQL 8.0-клиент не заменяет MySQL 8.4-клиент для этого режима.
